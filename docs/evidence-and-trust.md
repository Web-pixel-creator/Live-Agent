# Evidence and Trust

This document is the support surface for replay, signing, release evidence, and
operator-safe proof posture. Keep the primary seven-minute demo focused on the
product workflow; use this page when an operator, reviewer, or buyer asks how
the system proves what happened.

## Product Rule

The first screen should explain `AI Action Desk` before it explains runtime
machinery. Evidence and trust details stay in support surfaces:

1. `/app/console/runtime`
2. `/bundle/:id`
3. `/evidence/:id`
4. `docs/evidence-and-trust.md`

The current commercial wedge is still immigration teams. Local-services pilot
surfaces reuse the same trust posture, but they do not change the primary
product promise.

## What Counts As Evidence

Evidence should be compact, deterministic, and tied to an operator action.

1. `Case Outcome Summary` shows the business result for the seven-minute path.
2. `Presentation Bundle` and `Visual Evidence` show case-facing proof.
3. `Case Vault` shows compiled Case Wiki state, blockers, next action, and
   handoff posture.
4. `Operator Console` and `/app/console/runtime` show deeper replay, runtime,
   compliance, and artifact details.
5. Local-services pilot drawers copy reviewed planning payloads only; they do
   not send outreach, write CRM, create calendar bookings, sync analytics,
   bill, or mutate Markdown docs.

## Replay Posture

Replay proves the system did not rely on a hidden one-off UI state.

Required operator-readable signals:

1. session or case reference
2. latest verified proof
3. active workflow boundary
4. approval gate state
5. next operator action
6. recovery path when the boundary is blocked
7. evidence or bundle link

Raw replay lines are useful for debugging, but they should not be the first
surface a business operator sees.

## Signing Posture

Evidence signing is a trust layer, not a product headline.

When signing is configured, runtime evidence carries a tamper-evident envelope
with canonical hash metadata and signer posture. When signing is not configured,
the UI should say `Signature pending` or `unsigned` and point at the next
repo-owned step instead of pretending the proof is signed.

Operator-facing copy must distinguish:

1. proof published
2. proof pending
3. signature pending
4. export blocked by raw artifact posture
5. export blocked by compliance posture

## Release Evidence

Release evidence is generated by `npm run verify:release`.

The release gate should keep these artifacts aligned:

1. `artifacts/demo-e2e/summary.json`
2. `artifacts/demo-e2e/policy-check.json`
3. `public/demo-e2e/badge.json`
4. `public/demo-e2e/badge-details.json`
5. `artifacts/release-evidence/report.json`
6. `artifacts/release-evidence/runtime-proof-report.json`
7. `artifacts/release-evidence/action-desk-kpi-report.json`
8. `artifacts/release-evidence/consultation-booking-proof.json`

The badge can pass while deeper runtime proof reports still show warning
posture, for example unsigned evidence in a local environment. Treat that as a
support-surface finding, not as a reason to move runtime detail back into the
primary product screen.

## Local-Services Pilot Trust Rules

The local-services dispatcher pilot is manual-first until real pilot evidence
exists.

1. `Pilot workspace export drawer` is a planning export, not CRM sync.
2. `Manual activity log` records browser-local scorecard and metric events.
3. `Pilot daily log`, `Pilot week-one review`, and `Pilot evidence pack` are
   reviewed notes, not automated analytics or billing actions.
4. `Open discovery prep` and `Open day-one setup` prepare operator work; they
   do not create calendar events or customer messages.
5. `Open founder execution log` opens a redacted first-10-contact worksheet; it
   is not CRM, outreach send, booking, billing, analytics, or public
   customer-data storage.

Every local-services proof surface should preserve the same sentence:

`No external side effects.`

## Validation

For source or shell changes:

```bash
npm run test:unit
npm run build
```

For release-impacting changes:

```bash
npm run verify:release
```

For docs-only trust changes, at minimum run the source-level alignment test that
checks README, operator docs, local development docs, and this file stay linked.
